# 다중 사용자 실시간 동기화 개발 계획

작성일: 2026-10-08 / 상태: **1~4단계 구현됨**(부분 갱신인 5단계 미구현)

## 1. 목표

같은 레이어 데이터를 여러 사용자가 열어 둔 상태에서, 한 사용자가 편집(이동·회전·복제·삭제·속성 변경)을 **저장**하면 다른 사용자에게 알린다.

1. 1번 사용자가 저장한다.
2. 2번 사용자 화면에 "서버 데이터가 변경되었습니다. 갱신하시겠습니까?" 메시지가 뜬다(누가, 어느 레이어, 몇 개 객체인지 표시).
3. **예**를 누르면 변경된 데이터를 서버에서 다시 불러와 화면에 반영한다. **아니오**를 누르면 그대로 두고, 상태 표시줄에 "갱신 대기" 표시를 남긴다.

## 2. 현재 상태 (이미 있는 것과 없는 것)

| 항목 | 현재 |
|---|---|
| 저장 충돌 방지 | 있음. 저장할 때 `updated_at`을 비교하는 낙관적 동시성(`ApplyLayerEditsAsync`). 충돌한 객체만 건너뛰고 안내한다. |
| 다른 사용자의 변경을 알아채는 방법 | **없음**. 화면을 새로 불러오기 전에는 변경을 모른다. 편집을 시작한 뒤에야 저장 시점에 충돌로 알게 된다. |
| 변경 이력 | `audit_log`에 `drawing.save`(요약만)가 있다. 어떤 객체가 바뀌었는지는 없다. |
| 사용자 식별 | 로그인한 사용자(`AppUser`)와 감사 로그가 있어 "누가 바꿨는지" 표시할 수 있다. |
| 다시 불러오기 | `Refresh` 버튼이 전체를 다시 불러온다. 일부만 갱신하는 기능은 없다. |

## 3. 방식 선택

변경을 알리는 방법 두 가지를 비교했다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. PostgreSQL `LISTEN/NOTIFY`** (권장) | 이미 쓰는 DB만으로 동작한다. 별도 서버가 필요 없다. 거의 즉시 알린다. Npgsql이 기본 지원한다. | 앱이 DB 연결을 하나 계속 열어 둬야 한다. 연결이 끊긴 동안의 알림은 사라진다. 알림 크기는 8000바이트 이하여야 한다. |
| B. 주기적 조회(폴링) | 구현이 단순하다. 연결이 끊겨도 복구가 쉽다. | 확인 주기만큼 늦다. 사용자가 많으면 DB 부하가 늘어난다. |

**결정: A를 기본으로 쓰고, B를 안전망으로 함께 쓴다.** 알림 연결이 끊겼다가 다시 붙을 때와 일정 주기(예: 60초)마다 "내가 마지막으로 본 변경 번호 이후에 바뀐 게 있는지" 한 번 조회한다. 알림 유실을 이 조회가 메운다.

알림에는 변경 내용 전체를 싣지 않고 "변경 번호"만 싣는다. 받은 쪽이 변경 번호 이후의 변경 목록을 DB에서 읽어 온다. 이렇게 하면 알림 크기 제한과 유실 문제를 한 번에 피한다.

## 4. 데이터 모델

### 4.1 변경 로그 테이블

```sql
change_log (
  seq          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 변경 번호(증가)
  changed_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  user_id      BIGINT,           -- 저장한 사용자 (app_users.id)
  user_name    TEXT,             -- 이름 복사본(사용자 삭제 후에도 표시)
  session_id   UUID,             -- 저장한 앱 인스턴스 (자기 알림 무시용)
  layer_name   VARCHAR(255),
  entity_type  VARCHAR(30),      -- 'block_instance' | 'feature' | 'library'
  entity_id    BIGINT,
  op           CHAR(1)           -- 'I' 추가 / 'U' 수정 / 'D' 삭제
)
CREATE INDEX ON change_log (seq);
CREATE INDEX ON change_log (layer_name, seq);
```

- 저장 한 번(한 트랜잭션)에서 바뀐 객체마다 한 행씩 쓴다.
- 오래된 행은 정리한다(예: 30일 지난 행 삭제). 앱 시작 시 한 번 실행하면 된다.
- 삭제된 객체도 `op='D'`로 남아야 다른 사용자 화면에서 지울 수 있다.

### 4.2 알림 발송

변경 로그를 쓰는 같은 트랜잭션 안에서 `NOTIFY drawing_changed, '<최대 seq>'`를 보낸다. 트랜잭션이 커밋될 때만 알림이 나가므로 롤백된 저장은 알리지 않는다.

변경 로그는 **애플리케이션 코드에서 쓴다**(DB 트리거를 쓰지 않는다). 이유는 사용자·세션 정보를 같은 곳에서 넣을 수 있고, 지금 저장 코드(`ApplyLayerEditsAsync`)가 이미 한 트랜잭션으로 묶여 있기 때문이다. DXF Import와 삭제(`Del DXF`), 라이브러리 변경도 같은 방식으로 한 줄씩 기록한다.

## 5. 구성 요소

### 5.1 Infrastructure: `ChangeFeedRepository` (새 파일)

- `GetLatestSeqAsync()`: 현재 최신 변경 번호.
- `GetChangesSinceAsync(seq, layers)`: 번호 이후의 변경을 레이어·사용자별로 묶어 반환한다(`ChangeSummary`: 레이어, 사용자, 추가/수정/삭제 개수, 영향받은 객체 ID 목록).
- `PurgeOldAsync(days)`: 오래된 변경 로그 정리.
- `PostGisFeatureRepository.ApplyLayerEditsAsync` 등 저장 메서드에 변경 로그 기록과 `NOTIFY`를 추가한다. 사용자·세션 정보는 인자로 받는다.

### 5.2 Infrastructure: `ChangeListener` (새 파일)

- 전용 연결을 하나 열고 `LISTEN drawing_changed`를 실행한다. 이 연결은 쿼리에 쓰지 않는다.
- 알림을 받으면 이벤트(`ChangesAvailable`)를 올린다. 연결이 끊기면 재시도 간격을 늘려 가며(1, 2, 5, 10, 30초) 다시 연결하고, 다시 붙으면 즉시 한 번 조회해서 놓친 변경을 확인한다.
- 앱 종료·로그아웃·연결 정보 변경 시 정리한다.

### 5.3 App: 동기화 서비스와 화면

`MainWindow`에 `SyncCoordinator` 역할을 둔다(별도 클래스로 분리해 `MainWindow.xaml.cs`가 더 커지지 않게 한다).

1. 로그인·레이어 로드가 끝나면 최신 번호를 "기준 번호"로 저장하고 리스너를 시작한다.
2. 알림이나 안전망 조회로 변경을 확인한다. 아래는 무시한다.
   - 내가 저장한 변경(세션 ID가 같음).
   - 지금 화면에 로드하지 않은 레이어의 변경.
3. 남은 변경이 있으면 **갱신 확인 창**을 한 번 띄운다.
   - 내용: "홍길동 님이 Equipment 레이어의 객체 3개를 수정했습니다. 지금 갱신할까요?"
   - 여러 변경이 연달아 오면 2~3초 모아서 한 번만 묻는다. 이미 창이 떠 있으면 내용을 합쳐서 갱신한다.
   - **예**: 갱신 실행(5.4). **아니오**: 기준 번호는 그대로 두고 상태 표시줄에 "갱신 대기 (N건)"을 표시한다. 클릭하면 같은 확인 창을 다시 연다.
4. 상태 표시줄에 동기화 상태를 보여 준다: 연결됨 / 재연결 중 / 갱신 대기.

### 5.4 갱신 동작

확인 창에서 **예**를 눌렀을 때 상황별로 나눈다. 가장 신경 써야 하는 부분이다.

| 2번 사용자의 상태 | 갱신 방법 |
|---|---|
| **조회 모드** | 영향받은 레이어만 다시 불러와 다시 그린다(`ApplyEditMask` 등 기존 렌더 경로 재사용). 현재 줌·이동 위치와 선택은 유지하되 삭제된 객체의 선택은 해제한다. |
| **편집 모드, 미저장 변경 없음** | 조회 모드와 같이 갱신한 뒤 편집 대상(`editableSourcesById`)을 새 데이터로 교체한다. |
| **편집 모드, 미저장 변경 있음** | 내 변경과 겹치는 객체가 있는지 먼저 본다. 겹치지 않으면 서버 변경만 반영하고 내 변경은 유지한다. 겹치면 선택지를 보여 준다: ① 내 변경 버리고 서버 데이터로 갱신, ② 겹치는 객체는 내 것 유지(저장 때 충돌 안내), ③ 취소. |
| **갱신 중 다시 변경됨** | 갱신 시작 시점의 변경 번호를 기준으로 읽고, 끝난 뒤 그 번호를 새 기준으로 저장한다. 그 사이의 변경은 다음 알림에서 처리된다. |

- 부분 갱신(변경된 객체 ID만 다시 읽기)은 2단계에서 한다. 1단계는 **영향받은 레이어 전체 다시 불러오기**로 시작한다(구현이 단순하고 현재 레이어 규모에서 충분한지 측정한다).
- 편집 중인 객체를 다른 사용자가 삭제했다면, 갱신 후 그 객체는 "서버에서 삭제됨"으로 표시하고 저장 대상에서 뺀다.

## 6. 보안·권한

- 알림 채널은 같은 DB 계정을 쓴다. 별도 권한 키는 필요 없다(`drawing.view` 이상이면 변경 알림을 받는다).
- 변경 로그에는 객체 내용이 아니라 ID와 개수만 있어 정보 노출이 적다.
- 사용자 이름은 로그인한 앱 사용자 표시 이름을 쓴다.

## 7. 개발 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **1. 변경 로그** | `change_log` 테이블, 저장·Import·삭제 시 기록, 정리 작업, `ChangeFeedRepository` | 저장하면 변경 행이 생기고 롤백 시 생기지 않는다. 단위/통합 테스트 통과 |
| **2. 알림 수신** | `ChangeListener`(LISTEN/NOTIFY), 재연결, 안전망 조회, 자기 알림 무시 | 클라이언트 2개를 띄우고 한쪽 저장 시 다른 쪽에 이벤트 도착. 연결을 끊었다 복구해도 놓친 변경을 가져온다 |
| **3. 갱신 확인 창과 조회 모드 갱신** | 확인 창, 알림 묶음 처리, 상태 표시줄, 조회 모드에서 영향 레이어 다시 불러오기 | 1번이 저장하면 2번에 "갱신하시겠습니까?"가 뜨고, 예를 누르면 새 위치가 보인다 |
| **4. 편집 모드 갱신** | 편집 중 갱신 4가지 경우, 삭제된 객체 처리 | 편집 중인 2번에게 서버 변경이 안전하게 반영되고 내 미저장 변경은 사라지지 않는다 |
| **5. 부분 갱신과 확장** | 변경된 객체 ID만 갱신, 라이브러리 변경 알림(2단계 자동 갱신과 연계), 성능 측정 | 대형 레이어에서도 갱신이 1초 안에 끝난다 |

단계 1~3이 사용자가 요청한 핵심 기능이다. 단계 4는 편집 중 데이터가 사라지지 않게 하는 안전장치이므로 같은 릴리스에 넣는다.

## 8. 테스트 전략

- **단위 테스트**: 변경 묶음(`ChangeSummary`) 계산, 자기 세션 무시 규칙, 알림 묶음(디바운스) 규칙, 편집 충돌 판정(내 변경 ID와 서버 변경 ID의 교집합).
- **통합 테스트(실제 PostgreSQL, 임시 DB)**: 저장 → 변경 로그와 NOTIFY 발생, 롤백 시 미발생, 두 연결 사이 알림 전달, 연결 끊김 후 안전망 조회로 복구, 변경 로그 정리.
- **수동 시나리오**: 앱 2개(서로 다른 사용자) 실행 후 ① 이동 저장 ② 회전 저장 ③ 삭제 저장 ④ 편집 중 갱신(겹침/비겹침) ⑤ 아니오 후 재확인 ⑥ DB 재시작 후 복구.

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| 알림 연결이 조용히 끊겨 알림이 오지 않음 | 60초 주기 안전망 조회와 연결 상태 표시. 끊김을 감지하면 즉시 재연결 후 조회 |
| 변경이 몰려 확인 창이 계속 뜸 | 2~3초 묶음 처리, 창이 떠 있으면 내용 합치기, "아니오"는 상태 표시줄로 대기 |
| 대형 레이어 전체 다시 불러오기가 느림 | 5단계에서 부분 갱신. 그 전에 실제 레이어 크기로 시간 측정 |
| 편집 중 갱신으로 내 변경 손실 | 4단계의 겹침 판정과 선택지. 미저장 변경은 자동으로 덮어쓰지 않는다 |
| 변경 로그가 계속 커짐 | 보관 기간 정리(30일), `seq`·`layer_name` 인덱스 |
| 같은 DB 계정을 모두 공유 | 알림이 객체 내용을 싣지 않으므로 노출은 ID 수준. 근본 한계는 `LIBRARY_DESIGN.md` 7.4 참고 |
| DB를 앱 밖에서 직접 수정하면 알림이 없음 | 안전망 조회는 변경 로그만 보므로 못 잡는다. 필요하면 `updated_at` 최대값 비교를 보조로 추가 |

## 10. 결정이 필요한 사항

1. **갱신 방식**: 1단계는 "영향받은 레이어 전체 다시 불러오기"로 시작하는 것을 권장한다(부분 갱신은 5단계). 동의하는지.
2. **"아니오"를 눌렀을 때**: 상태 표시줄 "갱신 대기"로 남기는 안을 제시했다. 다시 묻지 않고 완전히 무시하는 방식을 원하는지.
3. **알림 대상**: 현재 화면에 로드한 레이어의 변경만 알리는 안을 제시했다. 로드하지 않은 레이어 변경도 알려야 하는지.
4. **편집 중인 사용자에게**: 편집 모드 중에도 확인 창을 바로 띄울지, 편집을 마치고 저장·취소한 뒤에 띄울지(편집 흐름을 덜 방해하는 후자도 가능).

## 11. 확정된 결정과 구현 결과 (2026-10-08)

**결정**: ① 레이어 통째 갱신(부분 갱신은 5단계) ② "아니오"는 상태 표시줄 "갱신 대기"로 남김 ③ 화면에 올린 레이어의 변경만 알림 ④ 편집 모드 중에는 묻지 않고 저장/취소 후에 묻는다.

**구현한 것**
- `change_log` 테이블과 `NOTIFY drawing_changed`: 저장(`ApplyLayerEditsAsync`), DXF Import, `Del DXF`가 같은 트랜잭션에서 기록·알림한다. 충돌로 건너뛴 객체와 롤백된 저장은 기록되지 않는다.
- `ChangeFeedRepository`(변경 조회·정리), `ChangeListener`(전용 연결 LISTEN, 1·2·5·10·30초 간격 재연결, 연결 직후 조회, 60초 안전망), `SyncCoordinator`(기준 번호, 2초 묶음 처리, "아니오" 기억).
- 확인 창: "서버 데이터가 변경되었습니다" + 사용자·레이어별 수정/추가/삭제 개수 → 예: 영향 레이어 전체를 다시 불러오되 줌·이동 위치와 숨긴 레이어는 유지한다. 아니오: 상태 표시줄에 "갱신 대기 (N건)", 클릭하면 다시 묻는다. 새 변경이 오면 다시 묻는다.
- 편집 모드 중에는 확인 창을 띄우지 않고 상태 표시줄에만 표시한다. 저장하거나 취소(편집 종료)하면 그때 묻는다. 편집 중 다른 사용자가 같은 객체를 바꿨다면 기존 `updated_at` 충돌 검사가 저장 때 안내한다. 따라서 4단계의 겹침 판정과 선택지는 만들지 않았다.
- 내가 저장한 변경(세션 ID 일치)과 화면에 올리지 않은 레이어의 변경은 무시한다. 변경 로그는 30일 지난 행을 앱 시작 때 정리한다.

**검증**: 임시 PostgreSQL DB에서 두 세션을 흉내 내 저장 → 알림 도착, 다른 세션의 요약(사용자·레이어·개수), 자기 세션 제외, 레이어 필터(대소문자 무시), 충돌 시 기록 없음, 정리를 확인했다. 연결 끊김 후 재연결과 화면 갱신 동작(확인 창, 줌 유지)은 실행해서 확인하지 못했다.
